# /close — 세션 마감 검증 (fresh 적대 검토 → §5 정리)

세션을 만든 컨텍스트는 자기 결과를 관대하게 본다. 마감 전에 **이 대화를 모르는 fresh 에이전트**가 "목표 대비 실제"를 검증한다 — 하네스 자체를 이 방식으로 검토해 Critical 1·Major 7을 잡아낸 실증(2026-08-08)의 세션판.

## 1. 검토 dispatch (`general-purpose` ×1 — fresh, fork ❌)

- 입력은 **목표와 파일 경로만** — 이 세션의 결론·자평·요약 전달 ❌ (오염 방지): 단위 목표(진행 중 `plan_v{N}` 파일 경로 전체 — 목표는 짝~검증 설계 절(템플릿 §0–§3), 대조 기준은 §TODO; 절 번호가 템플릿과 다른 plan은 절 이름으로 대응; 없으면 이번 세션 목표 1줄), 검토 대상(변경 파일 목록, `done_v{N}`, `progress.md`, 실행 산출물·로그 경로).
- 검증 항목: ① plan §3 성공 임계값 vs done §2 수치 — 근거 원천(metrics.json·eval 출력) 실재하는가 ② plan §6 체크 항목 vs 실제 파일·diff 일치하는가 ③ "완료" 주장 중 실행 출력·산출물 없는 것 ④ 세션 종료 계약 누락 — plan §5 로그·progress 3종(타임라인/Matrix/헤더)·LEARNINGS ⑤ 목표와 산출물의 갭(했다고 한 것 vs 실제 한 것).
- 발견 형식: 심각도 + 파일:줄 근거. 발견 없으면 없다고 명시하게 한다.

## 2. 반영

- 사실 오류·계약 누락은 즉시 수정(SOFT — 수정한 줄을 보고에 표시).
- **verdict를 뒤집는 발견**(수치 불일치·미검증 완료 주장)은 사용자 보고 후 대기(HARD) — done §3 재작성은 confirm 후.
- 재검토는 기본 없음 — thesis-level claim이 뒤집혔을 때만 1라운드 추가(`/harness` §4 리뷰 규칙과 동일).

## 3. §5 정리 수행

`/harness` §5 세션 종료 계약 그대로: plan §6 체크·§5 로그·(done 단위 후) progress 3종·종료 보고(verdict 1줄 + 기승전결). 검토에서 반영 못 한 발견은 종료 보고에 명시 — 숨기고 닫기 ❌.

## 하지 않는 것

- 이 세션 컨텍스트를 상속한 fork로 검토 ❌ — fresh여야 의미가 있다.
- 검토자에게 이 세션의 자평·결론 전달 ❌ — 파일과 목표만.
- 검토 발견 숨기고 닫기 ❌.
- git commit/push ❌ (사용자 몫).
